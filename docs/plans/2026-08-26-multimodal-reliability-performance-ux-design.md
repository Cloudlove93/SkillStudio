# 多模态蒸馏可靠性、性能与交互整改设计

## 背景与已确认问题

真实课堂视频已经完成媒体预处理，生成 244 段转录、502 条证据和 7 个语义时刻。失败发生在候选 Skill 校验阶段：五路提取共生成 38 个候选，随后逐个串行校验，最终融合又携带全部证据形成约 47 万字符请求；模型返回重复 evidenceId 后，严格契约和一次重生成均失败。

前端同时把后续候选阶段的全局错误显示在转录内容附近，并且播放器停在 0:00 时采用严格区间匹配，导致第一条证据从 0.82 秒开始时显示“0 条”。内容概览默认展开过多长文本，页面层级和操作焦点不清晰。

## 目标

- 已成功的转录、证据和内容概览不被后续失败覆盖。
- 对无语义影响的重复 ID 做确定性修复，继续拒绝未知、伪造或越界引用。
- 候选生成、校验和融合采用有界并发、有界数量和最小必要上下文。
- 页面每次只突出一个当前任务，长内容通过稳定抽屉查看，不在主页面原地无限展开。
- 不新增数据表，不新增 FK 或 CHECK，不删除对象存储数据。

## 后端设计

1. 候选契约边界在严格解析前仅对 evidenceIds 去重，保持首次出现顺序。其他字段、未知 ID、空引用、错误枚举和非法 candidateId 仍由共享契约拒绝。
2. 五路候选提取以最多 3 路并发执行，每路只接受最多 4 个候选；服务端确定性截断作为模型不遵守数量要求时的最后保护。
3. 候选校验按 3 个并发任务成波次执行，输出仍按输入候选顺序合并，保证结果可复现。
4. 融合请求仅包含保留候选实际引用的证据，不再携带完整 evidenceTimeline；融合结果仍以完整证据 allowlist 做最终校验。
5. 继续保留单次契约重生成，但归一化后不因重复 ID 触发昂贵重生成。阶段失败只记录对应的 `resumeStage`。

## 前端设计

1. `evidenceAtTime` 优先返回当前命中；没有命中时返回最近的下一组证据，超过合理窗口则返回最近上一组，并向播放器显示“即将出现/最近证据”，不再用“0 条”暗示证据缺失。
2. 错误卡依据 `error.stage` 映射到处理、内容、候选或发布步骤；候选校验失败在“选择 Skill”步骤呈现，转录抽屉保持可用。
3. 内容概览主页面每层只显示一条摘要，统一使用抽屉查看该层全部结论；主页面不再原地展开成长列表。
4. 质量降级提示汇总为紧凑入口；媒体、当前任务和底部主操作形成稳定三层结构。
5. SSE 连接正常时只做低频数据库校对；降级轮询采用递增间隔并防止请求重叠，减少闪烁和重复渲染。

## 验收指标

- 重复 evidenceId 的真实模型响应可被安全归一化，未知 evidenceId 必须失败。
- 五路提取最大并发为 3；候选校验最大并发为 3；最终顺序稳定。
- 融合请求不得包含未被保留候选引用的证据。
- 0:00 可以看到第一组即将出现的证据及时间提示。
- `validating_candidates` 失败不会显示在转录证据库语境内。
- 使用指定高等数学视频跑通到“选择 Skill”，记录每阶段耗时。
- server/web lint、测试、构建、Docker 构建和浏览器验收全部通过。
