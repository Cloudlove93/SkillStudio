# 代码评审规范

> 依据课件第三部分 126–171 页的 Code Review 要求，结合当前仓库整理。
> 关联文档：[development-process.md](./development-process.md)、[code_quality.md](./code_quality.md)、[architecture.md](./architecture.md)。

## 1. 目标

代码评审的目标是**改善代码和共享知识**，不是寻找个人错误。

- 在合并前发现需求偏差、架构越界、安全风险和测试缺口。
- 让团队成员理解变更背景、影响范围和后续维护方式。
- 把评审意见变成可执行的修改，而不是模糊结论。

## 2. PR 要求

仓库已提供 `.github/pull_request_template.md`，创建 PR 时会自动带出模板。

### 2.1 规模

- 一个 PR 只做一个主要变化。
- 尽量控制在约 400 行 diff 以内；超过时说明原因并拆分。
- 重构与功能变更分开提交/分开 PR。

### 2.2 标题

使用 Conventional Commits 风格：

```text
feat(agent): 增加课例包 Agent 模板
fix(workflow): 修复保存后 Skill 绑定丢失
refactor(package): 拆分 rubric 抽取逻辑
test(skill): 补充版本回滚回归测试
docs(quality): 补充质量门禁说明
```

### 2.3 描述模板

```markdown
## 变更目的

<!-- 解决什么问题，关联哪个 Issue -->

## 影响范围

<!-- 前端/后端/数据库/Agent/Skill/工作流/部署 -->

## 验证方式

- [ ] 单元测试
- [ ] 契约测试
- [ ] 手工验证（写明路径与步骤）
- [ ] 其他

## 风险与回滚

<!-- 兼容性、数据迁移、版本冲突、灰度或回滚方式 -->

## 截图/日志

<!-- UI 变更附截图；接口变更附请求/响应示例 -->
```

## 3. 评审清单

### 3.1 需求与架构

- [ ] 是否正确实现需求和验收标准？
- [ ] 是否符合现有架构和模块边界？
- [ ] 是否引入了不必要的抽象、依赖或复杂度？
- [ ] 是否影响已有 Agent / Skill / 工作流 / 会话的兼容性？

### 3.2 安全

- [ ] 输入是否校验，输出是否编码？
- [ ] 鉴权、资源隔离、越权访问是否覆盖？
- [ ] 是否存在 SQL 注入、XSS、命令注入、SSRF 等风险？
- [ ] 是否避免硬编码密钥、Token 或用户隐私？
- [ ] 日志是否泄露敏感信息？
- [ ] 新依赖是否必要，许可证是否可接受？

### 3.3 正确性与边界

- [ ] 异常、空值、边界条件和超时是否处理？
- [ ] 并发、幂等和版本冲突是否正确处理？
- [ ] 失败时是否会留下半成品或错误状态？
- [ ] 是否存在可回滚路径？

### 3.4 测试

- [ ] 新增行为是否有测试？
- [ ] 缺陷修复是否有回归测试？
- [ ] 是否覆盖关键失败场景，而不只是正常路径？
- [ ] 测试是否稳定，是否依赖真实外部服务或时间？

### 3.5 可维护性

- [ ] 命名、职责和依赖关系是否清晰？
- [ ] 是否存在重复逻辑或过大文件？
- [ ] 是否引入不必要的复杂度？
- [ ] 文档、注释和类型是否同步更新？

### 3.6 性能与可观测性

- [ ] 是否引入明显的 N+1 查询、重复请求或大对象拷贝？
- [ ] 是否影响启动、构建或页面加载时间？
- [ ] 日志是否足以定位问题？
- [ ] 是否影响 `/readyz`、健康检查或超时配置？

## 4. 本项目重点评审区域

| 区域 | 重点 |
| --- | --- |
| Agent / Skill 版本 | `expectedUpdatedAt`、409 冲突、版本回滚、快照一致性 |
| 仓库 Skill | 跨包复制、`originPackageId`、权限隔离、删除后的引用 |
| 工作流 | 保存校验、仓库 Skill 解析、试跑失败定位、节点重试 |
| 课例资产 | manifest → index → Skill 目录一致性、不要编造课例 |
| 鉴权 | Kong/JWT、`X-User-Id` 注入、越权访问 |
| 媒体 | 上传校验、签名 URL、Worker 超时与清理 |
| 部署 | Docker Compose、环境变量、健康检查、回滚 |

## 5. 意见分级

| 级别 | 含义 | 是否阻断合并 |
| --- | --- | --- |
| `[Must]` | 必须修改：正确性、安全、数据一致性、需求偏差 | 是 |
| `[Should]` | 建议修改：可维护性、测试补充、性能改进 | 通常建议修改后再合并 |
| `[Question]` | 需要讨论：设计取舍、边界不清 | 讨论后再决定 |
| `[Nit]` | 细节问题：命名、格式、注释 | 否 |

评审意见要写清楚：

- 问题是什么。
- 为什么是问题（风险/影响）。
- 建议怎么改，或给出可接受的替代方案。

## 6. 评审流程

```text
作者自检 → 提交 PR → CI 通过 → 评审 → 修改 → 再评审 → 合并
```

要求：

- 作者先完成自检清单，再请求评审。
- 评审人尽量在 24 小时内给出首轮反馈。
- 涉及架构、数据迁移、鉴权、版本快照的变更，至少 2 人评审。
- 大规模修改或方向性调整，先讨论方案再写代码。
- 紧急修复可以事后补评审，但必须记录原因和验证方式。

## 7. 评审禁区

- 不做人身评价，不使用「你怎么又……」这类表述。
- 不以「风格不喜欢」作为阻断理由；格式问题交给工具。
- 不要求作者在同一个 PR 里顺手重构无关代码。
- 不在没有测试和验证的情况下要求「先合并再说」。
- 不绕过 CI、不跳过评审、不直接推送 `main`。

## 8. 合并后

- 确认 CI 与部署状态。
- 观察关键指标：错误日志、构建失败率、接口错误率。
- 如发现回归，优先回滚或关闭开关，再定位根因。
- 把可复用的经验补充到本文档或团队知识库。
