## 0. 一页结论

实现阶段不等于「写代码」，而是一个闭环：

```text
任务拆分 → 编码实现 → 本地构建与测试 → Git 提交 → 代码评审 → CI 自动化验证 → 重构与质量改进 → 可交付构件
```

课件反复强调的四件事：

1. **清晰任务**：复杂需求拆成可执行、可独立验证的小任务。
2. **高质量代码**：清晰、可维护、可测试，而不是追求更多代码。
3. **自动化验证**：用测试、静态检查和 CI 尽早发现问题。
4. **协作交付**：通过 Git、代码评审和反馈持续集成。

一句话：**实现阶段的核心是持续交付可信赖的软件变更，不是写出更多代码。**

## 1. 开发流程七步

| 步骤 | 课件要求 | 本项目落地方式 |
| --- | --- | --- |
| 1. 任务拆分 | 目标明确、修改范围清晰、可独立验证、有完成标准、周期短 | GitHub Issue + 任务编号；一个 PR 只做一个主要变化 |
| 2. 编码实现 | 模块职责清晰、接口稳定、依赖合理、异常/边界完整、数据校验、并发与资源安全、日志可定位 | `educlaw-server` 的 route/service 分层；`educlaw-web` 的组件与状态分离 |
| 3. 本地验证 | 单元测试、必要的集成测试、本地构建、静态检查 | `pnpm lint`、`pnpm check:types`、`pnpm test`、`pnpm build` |
| 4. 代码提交 | 小步、独立、可理解；提交信息说明「做了什么」 | Conventional Commits：`feat/fix/refactor/test/docs/chore` |
| 5. 代码评审 | 正确性、架构边界、安全、异常边界、测试、复杂度、性能与可维护性 | 每个 PR 至少 1 人评审；使用 `code_review.md` 清单 |
| 6. CI 验证 | 编译、格式、静态分析、单测、集成测试、构件、反馈 | 当前缺失；需要补 `.github/workflows/ci.yml` |
| 7. 重构改进 | 先有测试保护、小步修改、重构不与大功能混合、记录技术债 | 单独 `refactor/*` 分支与 PR；在 `code_quality.md` 记录技术债 |

## 2. 编码规范与技术原则

### 2.1 编码关注点

- 模块职责是否清晰
- 接口设计是否稳定
- 依赖关系是否合理
- 异常和边界条件是否处理
- 数据校验是否完整
- 并发和资源释放是否安全
- 日志是否足以支持问题定位

### 2.2 技术原则

- 高内聚、低耦合
- 单一职责
- 面向接口编程
- 依赖倒置
- 封装变化
- 避免重复代码
- 避免过早优化

> 代码首先应当正确，其次应当清晰，最后才是针对真实瓶颈进行优化。

### 2.3 工具选型

| 场景 | 课程推荐 | 本项目现状 |
| --- | --- | --- |
| TypeScript / JavaScript | ESLint、Prettier、TypeScript | 已有 ESLint + TypeScript；Prettier 有配置与 format 脚本 |
| Python | Ruff、Black、mypy、Pylint | 媒体 Worker 有 Python 代码，建议补 Ruff/Black 检查 |
| 多语言质量分析 | SonarQube、Semgrep | 未接入 |
| 依赖漏洞 | Snyk、Dependabot、OWASP Dependency-Check | 有 `pnpm security:audit`，未纳入 CI |

## 3. Git 分支与提交规范

### 3.1 推荐工作流

```text
主干分支 → 创建功能分支 → 本地开发 → 提交 Commit → Push → Pull Request → 代码评审 → 合并主干
```

要求：

- 每项任务使用独立分支
- 分支名称包含任务编号
- 提交保持小步、独立、可理解
- 通过 Pull Request 合并代码
- 保护主干分支
- 合并前必须通过自动检查

### 3.2 Conventional Commits

```text
feat: 增加订单创建接口
fix: 修复库存扣减并发问题
refactor: 重构用户认证模块
test: 增加订单服务单元测试
docs: 更新接口使用说明
chore: 升级项目依赖
```

良好提交的特征：

- 一个提交完成一个主要逻辑变化
- 提交信息说明「做了什么」
- 不提交无关格式修改
- 不提交生成文件和敏感信息
- 必要时说明原因

### 3.3 本项目注意

- README 已约定 `main` / `develop` / `feature/*` / `fix/*` 分支。
- 当前工作分支为 `integrate/p1-asset-center`，继续保持「一项修改一个分支、验证后审核」。
- **`.preview.env` 含 LLM API Key，必须加入 `.gitignore`，禁止提交。**
- 生成目录、构建产物、日志、临时脚本不进入提交。

## 4. Code Review

### 4.1 评审方面

- 是否正确实现需求和验收标准
- 是否符合架构和模块边界
- 是否存在安全漏洞
- 异常和边界条件是否完整
- 测试是否覆盖关键逻辑
- 是否引入不必要的复杂度
- 是否影响性能和可维护性

### 4.2 评审原则

- 小型 Pull Request 更容易高质量评审
- 评论代码，不针对个人
- 解释问题和风险，而不是只给结论
- 对重要设计问题进行讨论
- 评审意见应当可执行

> 代码评审的目标是改善代码和共享知识，不是寻找个人错误。

### 4.3 本项目落地

- 新建 `docs/software/code_review.md`，包含 PR 模板与检查清单。
- PR 描述至少包含：变更目的、影响范围、验证方式、风险与回滚方案。
- 涉及 Agent 版本、Skill 快照、工作流校验、鉴权的改动，必须写明兼容性与数据迁移影响。
- 代码评审意见分为「必须修改 / 建议修改 / 讨论」三档，避免模糊结论。

## 5. 测试策略

### 5.1 测试层次

| 层次 | 目标 | 本项目现状 |
| --- | --- | --- |
| 单元测试 | 验证独立函数或模块，速度快、定位准 | 前端 439 项、后端 Vitest、Python Worker 测试 |
| 集成测试 | 验证模块协作、数据库/缓存/消息交互 | 后端有集成测试；建议补关键链路 |
| 接口测试 | 验证 API 输入、输出、错误处理、契约稳定 | 前端 117 项契约测试；后端 API 测试 |
| 端到端测试 | 验证完整业务流程，覆盖关键路径 | 尚未形成稳定 E2E 套件 |

### 5.2 常用测试技术

等价类划分、边界值分析、判定表、状态迁移测试、参数化测试、Mock/Stub、契约测试、属性测试、变异测试。

### 5.3 工具

| 场景 | 课程推荐 | 本项目 |
| --- | --- | --- |
| TypeScript/JavaScript | Jest、Vitest、Supertest | Vitest、node:test、Supertest 风格契约测试 |
| API | Postman、REST Assured | 契约测试 + 后端 API 测试 |
| Web UI | Playwright、Cypress、Selenium | 暂无稳定 E2E |
| 性能 | JMeter、k6、Gatling、Locust | 暂无 |

> 测试覆盖率是辅助指标，不等于软件质量。关键是测试是否覆盖重要行为、边界条件和失败场景。

### 5.4 本项目优先补的测试

1. Agent 创建 → 保存 → 对话的完整链路（E2E 或接口级集成）。
2. Skill 版本创建、回滚、Agent 重绑定的版本一致性。
3. 工作流保存校验与试跑（含仓库 Skill 解析）。
4. 鉴权与资源隔离（越权访问必须失败）。
5. 课例包生成与 manifest → index → Skill 目录的一致性。

## 6. 构建与 CI

### 6.1 构建过程

1. 获取依赖
2. 编译源代码
3. 执行静态检查
4. 运行自动化测试
5. 生成构件
6. 记录版本和构建信息

### 6.2 构建实践

- 锁定依赖版本（`pnpm-lock.yaml`）
- 使用统一构建命令（`pnpm build`）
- 构建结果可重复
- 缓存稳定依赖
- 生成可追踪的构件版本（Docker 镜像 tag）
- 定期更新和审计第三方依赖

### 6.3 CI 设计原则

- 快速反馈
- 自动化执行
- 失败立即通知
- 构建环境一致
- 不允许失败代码进入主干
- Pipeline 配置也纳入版本控制

### 6.4 本项目缺口

当前 `.github/workflows` 只有 README 占位，没有实际 CI。建议补 `ci.yml`，至少包含：

```text
pnpm install --frozen-lockfile
pnpm lint
pnpm check:types
pnpm test
pnpm build
pnpm security:audit
```

可选增强：

- 前端覆盖率报告
- 后端集成测试（PostgreSQL service container）
- Docker 构建检查
- Semgrep / CodeQL / Trivy
- 密钥扫描（gitleaks）

- 日志不输出 token、密码、用户隐私和完整请求体。

## 8. 重构与技术债务

### 8.1 什么时候需要重构

- 代码重复严重
- 模块职责混乱
- 修改一个功能需要影响多个模块
- 测试难以编写
- 缺陷频繁出现
- 新功能开发速度持续下降

### 8.2 常见重构方式

提取函数和类、拆分过大的模块、消除重复逻辑、引入接口隔离依赖、改善命名、简化条件分支、重构数据访问逻辑。

### 8.3 重构原则

1. 先建立测试保护网
2. 小步修改
3. 每次修改后运行测试
4. 不将重构和大规模功能变更混在一起
5. 记录技术债务及其影响

### 8.4 本项目重构候选（不在本轮强制完成）

| 文件 | 行数 | 说明 |
| --- | --- | --- |
| `educlaw-server/src/services/package-service.ts` | 约 3590 | 包生成、rubric 抽取、导入导出、版本对比混在一起，后续可拆模块 |
| `educlaw-server/src/services/skill-version-service.ts` | 约 2057 | 仓库查询、版本分配、导出逻辑可继续分层 |
| `educlaw-web/src/pages/SkillFirstWorkspace.tsx` | 约 2417 | 页面编排与业务状态较多，可拆 hook/子视图 |
| `educlaw-web/src/pages/WorkflowDemo.tsx` | 约 934 | 画布、节点库、配置面板可拆组件 |
| `educlaw-web/src/lib/studio-presets.ts` | 约 900 | 预置资产数据与推荐逻辑可拆数据/匹配模块 |

原则：先补测试，再小步拆；不要把重构和新功能放在同一个 PR。

## 9. AI 辅助编码

### 9.1 AI 适合辅助的任务

- 生成样板代码
- 编写单元测试
- 解释陌生代码
- 生成 API 文档
- 辅助代码重构
- 分析错误日志
- 生成 SQL、脚本和正则表达式
- 总结 Pull Request

### 9.2 工程师必须负责

- 验证业务逻辑
- 审查架构影响
- 检查安全风险
- 确认性能和资源消耗
- 运行测试和静态检查
- 避免泄露敏感信息
- 确认第三方代码许可

> AI 可以生成代码，但不能替代工程判断。

### 9.3 推荐流程

```text
明确任务和约束 → 提供必要上下文 → 生成或修改代码 → 人工审查 → 自动化测试 → 静态与安全检查 → 代码评审 → 合并代码
```

使用原则：

- 先明确输入、输出和验收标准
- 要求 AI 说明修改思路和影响范围
- 限制修改文件和代码范围
- 不直接接受未经验证的结果
- 将 AI 生成代码视为普通外部贡献
- 通过测试、评审和 CI 建立质量保障

## 10. 质量门禁与工程度量

### 10.1 进入主干前至少满足

- 编译或构建成功
- 格式检查通过
- 静态分析通过
- 单元测试通过
- 关键集成测试通过
- 依赖漏洞检查通过
- 代码评审完成
- 没有泄露敏感信息
- 变更说明完整
- 必要的文档已更新

示例：

```text
Build              PASS
Unit Tests         PASS
Integration Tests  PASS
Static Analysis    PASS
Security Scan      PASS
Code Review        APPROVED
```

### 10.2 工程度量

| 维度 | 指标 |
| --- | --- |
| 交付效率 | 任务完成周期、PR 周期、构建耗时、部署频率、评审等待时间 |
| 代码质量 | 缺陷密度、单元测试覆盖率、静态分析问题数、重复代码比例、代码复杂度、技术债务规模 |
| 流程稳定性 | 构建失败率、测试失败率、变更失败率、缺陷逃逸率、回滚次数 |

> 度量指标应服务于改进，而不是简单用于评价个人绩效。

### 10.3 本项目建议

- 先记录 2 周基线，不设虚假目标数字。
- P0 门禁必须 100% 通过：构建、lint、类型检查、单测、契约测试、代码评审、无敏感信息。
- 覆盖率先统计核心服务与关键链路，不追求全仓库统一数字。
- 每周记录一次构建失败率、测试失败率、变更失败率和回滚次数。

## 11. 典型任务模板

- 重复请求（幂等）
- 日志中不出现敏感信息

## 13. 讨论题与初步立场

课件给出的讨论题：

1. 为什么代码评审不能完全由自动化工具替代？
2. 测试金字塔是否适用于所有类型的软件系统？
3. Trunk-Based Development 与 Git Flow 如何选择？
4. 如何判断一次重构是否真正降低了技术债务？
5. AI 生成代码应当经过哪些质量门禁？
6. 如何设计一个既快速又可靠的 CI Pipeline？
7. 代码覆盖率、缺陷密度和变更失败率之间有什么关系？

团队初步立场：

- **代码评审**覆盖设计意图、上下文、风险和知识共享，自动化只能覆盖可规则化部分。
- **测试金字塔**不是教条；本项目更适合「单元 + 契约 + 少量关键 E2E」，不以 E2E 数量取胜。
- **分支模型**：小团队、短周期用短分支 + PR；如果发布节奏稳定，可转向 Trunk-Based，减少长期分支漂移。
- **重构是否降低技术债**：看复杂度、重复率、变更失败率、缺陷逃逸率是否改善，且测试保持通过；不能只看代码行数。
- **AI 生成代码**必须经过与人工代码相同的门禁，并额外记录来源、审查范围和许可证风险。
- **CI 设计**：缓存依赖、并行任务、失败快速反馈，目标控制在 10 分钟内；CI 配置纳入版本控制。
- **覆盖率**是必要但不充分指标；同时看缺陷逃逸率和变更失败率，避免「为覆盖率写测试」。
